## CUDA Profile

g64 profile 包裹了 `performance_small` 中的一个请求，远程 trace 路径为
`/tmp/baseline-small-g64-profile.json`（736 MiB，未提交到仓库）。profile 总计
39.667 秒 CPU 时间和 40.419 秒 CUDA 时间。按 CUDA self time 排序的主要条目如下：

| 算子 | CUDA self time | 占比 | 调用次数 |
| --- | ---: | ---: | ---: |
| `aten::copy_` | 18.943 s | 46.87% | 83,630 |
| unrolled elementwise kernel | 9.538 s | 23.60% | 10,496 |
| 128-thread elementwise kernel | 9.280 s | 22.96% | 20,992 |
| `aten::mul` | 9.073 s | 22.45% | 41,344 |
| Command Buffer Full | 6.276 s | 15.53% | 58,832 |
| `aten::sub` | 5.920 s | 14.65% | 11,777 |
| `aten::mm` | 3.524 s | 8.72% | 10,528 |

profile 百分比来自不同层级的 self activity，可能相互重叠，不能直接相加。大量
copy、位移/掩码和逐元素 kernel 表明 reference INT4 路径反复执行权重解包和反量化，
并发射大量小 kernel；矩阵乘不是当前最大的 self-time 来源。

## 基线结论

1. 在静态 KV Cache 和 eager attention 配置下，当前 10 GiB 显存无法完成 public
   workload，g64/g128 都会触发同类问题。第一优先级是降低 attention 临时显存，并
   将 KV 分配改为按需使用。
2. 对能够运行的请求，主要延迟来自 INT4 reference 反量化路径（`copy_`、逐元素
   运算和同步），而不只是 GEMM。fused 反量化加矩阵乘是首要 kernel 优化方向。
3. 后续实验应固定上述条件，重新运行短测试和单请求 CUDA profile，并记录完整 public
   队列是否能够结束。

| 输入长度区间 | 请求数量 |
| --- | ---: |
| 0-512 | 4 |
| 512-1024 | 2 |
| 1024-2000 | 4 |

| 输出长度区间 | 请求数量 |
| --- | ---: |
| 0-16 | 3 |
| 16-32 | 4 |

最大输出 token 数为 `3*16 + 4*32 + 3*48 = 288`。若总时间目标为 36 秒，
仅按输出 token 计算就需要至少 `288/36 = 8 tokens/s`，还要为 10 条请求的
prefill 留出时间。因此目标需要显著高于当前 small g64 测得的 `0.788 tokens/s`，
不能依靠单一开关完成。

## 基于 Profile 的优化路线

### P0：先解决长 prompt 显存峰值

当前 eager attention 显式创建 `QK^T`、float mask 和 softmax probability，长 prompt
会产生 `O(Q*K)` 的临时显存；`KVCache.allocate()` 还按最大长度静态预留 cache。

1. 将 full/sliding attention 改为 `scaled_dot_product_attention`，优先使用 H800
   可用的 fused/FlashAttention kernel，避免物化完整 score/prob。
2. 引入 128/256 token 的 chunked prefill。chunk 之间递增写入 KV，只有最后一个
   chunk 产生采样 logits，避免一次性处理 2000 token。
3. 将连续 KV 改为按 16/32 token block 的 paged cache；sliding-window layer 使用
   ring buffer，并在请求结束时立即回收 block。

### P0：消除 INT4 reference 的反量化临时张量

profile 中 `aten::copy_` 占 46.87%，elementwise kernel 约 23%，`aten::mul` 占
22.45%，而 `aten::mm` 只有 8.72%。这与 `QuantizedLinear.forward()` 每次先
`unpack_int4 -> 转 BF16 -> scale/zero point -> F.linear` 的实现完全对应。

优先实现 Triton/TileLang fused W4A16 GEMM：在 kernel 内读取 packed nibble 和 scale，
直接完成反量化与矩阵乘，避免完整 BF16 权重、中间 copy、位移和逐元素 kernel。应
分别针对 prefill 的大 `M` 和 decode 的 `M=active_batch` 做 autotune，并以 g64
精度结果为门槛（g128 虽略快，但此前 `delta_nll` 约为 0.121）。

### P1：提高有效 decode batch

`StaticBatchScheduler` 会固定 batch 到所有请求结束，输出长度 16/32/48 会产生拖尾。
在 paged KV 可用后，实现 continuous batching：

- 按输入长度分桶，减少 padding；
- prefill 与 decode 分离，并限制每轮 prefill token budget；
- 每轮移除完成请求、回收 KV block、补入等待队列；
- 测试显存允许的 `batch_size=2` 和 `4`，以提高 decode GEMM 的有效矩阵尺寸。

### P1/P2：减少额外 kernel 和同步

- 使用 GQA 原生 attention，避免 `repeat_kv()` 物化 KV；
- 复用 position/mask tensor，避免每层重复 `arange/clone/masked_fill`；
- 减少 decode 中 `next_tokens.tolist()` 引起的 GPU-CPU 同步；
- `torch.compile` 只作为验证项，不能用关闭同步来替代正式计时。

### 验证顺序

每轮优化都应在完整 `performance_public.jsonl` 上验收，并同时 profile 代表形状：
prefill 的约 256/768/1536 token，以及 decode 的 active batch 1/2/4、历史长度
512/1024/2000、输出长度 16/32/48。验收条件为 public 10 条请求全部完成、
`elapsed_s <= 36`、`delta_nll < 0.1`，并记录 TTFT、TPOT、峰值显存和关键 kernel
延迟变化。
