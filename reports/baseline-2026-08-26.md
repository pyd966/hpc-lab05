The g64 short-workload row is the reference baseline for subsequent optimization rounds.
The two public runs both fail before producing a summary: the eager prefill allocates a
large temporary attention tensor after the static KV cache has been allocated. The g128
run reports an attempted 250 MiB allocation with only 80 MiB free, followed by repeated
500 MiB allocation failures. The `UnboundLocalError` reported at
`engine.py:113` is a secondary exception after the CUDA allocation failure, not the
capacity limit itself.

## CUDA profile

The g64 profile wrapped one request from `performance_small` and was exported remotely as
`/tmp/baseline-small-g64-profile.json` (736 MiB; intentionally not committed). The
profile totals are 39.667 s CPU and 40.419 s CUDA. Top entries sorted by self CUDA time:

| Operation | Self CUDA | Share | Calls |
| --- | ---: | ---: | ---: |
| `aten::copy_` | 18.943 s | 46.87% | 83,630 |
| unrolled elementwise kernel | 9.538 s | 23.60% | 10,496 |
| 128-thread elementwise kernel | 9.280 s | 22.96% | 20,992 |
| `aten::mul` | 9.073 s | 22.45% | 41,344 |
| Command Buffer Full | 6.276 s | 15.53% | 58,832 |
| `aten::sub` | 5.920 s | 14.65% | 11,777 |
| `aten::mm` | 3.524 s | 8.72% | 10,528 |

Profiler percentages are per-entry and can overlap because PyTorch reports nested
activities; they must not be summed. The high call counts and the dominance of copies,
shifts/masks, and elementwise kernels indicate that the reference INT4 path repeatedly
unpacks/dequantizes weights and launches small kernels. Matrix multiplication is not the
largest self-time entry in this baseline.

## Baseline conclusions

1. The current 10 GiB device cannot complete the public workload with static KV allocation
   and eager attention, independent of the g64/g128 choice. Reducing attention temporary
   memory (fused/FlashAttention or chunked prefill) and making KV allocation demand-driven
   are the first capacity optimizations.
2. For requests that fit, the main measured latency signal is the INT4 reference
   dequantization path (`copy_`, elementwise arithmetic, and synchronization), not only
   GEMM. A fused dequantize-plus-GEMM path is the primary kernel optimization hypothesis.
3. Future rounds should keep the conditions above fixed, rerun the short throughput
   check and a one-request CUDA profile, and record whether the full public queue finishes.
