# Triton 反量化-GEMM 融合实验报告

日期：2026-08-27

## 本轮目标与约束

本轮消除 `QuantizedLinear.forward()` 中
`unpack_int4 -> BF16/FP16 临时权重 -> F.linear` 的完整反量化张量。CUDA 优化路径使用
项目内自行编写的 Triton kernel，没有调用 FlashAttention、xFormers、bitsandbytes、
cuBLASLt 封装、PyTorch SDPA 或其他现成量化 GEMM 算子。

量化 checkpoint 仍为长期缓存：

    /home/h3250106394/quantized/gemma-4-12b-gptq-group64

本轮只读取其中的 packed INT4、FP16 scale 和 manifest，没有重新执行 GPTQ，也没有永久
保存或缓存完整 BF16/FP16 权重。

## Kernel 设计

实现位于 `src/hpc101_infer/kernels/w4a16.py`，CUDA 路径的数据流为：

1. 从 `[N, padded_K / 2]` 的 `uint8` qweight 读取 packed byte；
2. 按 `uint8_little_nibble` 约定，以低 nibble 解码偶数 K、高 nibble 解码奇数 K；
3. 根据 `floor(k / group_size)` 加载每个输出通道的 scale 和可选 zero point；
4. 在当前 K tile 内将 INT4 code 转为 BF16/FP16，立即执行 `tl.dot`；
5. 使用 FP32 accumulator，融合可选 bias，最后写回输入 dtype 的输出。

kernel 只遍历原始 `in_features`，因此末尾 padding 不参与乘加；qweight、scale、zero
和 bias 均直接使用现有 tensor stride。对称量化采用 `(q - 8) * scale`，非对称量化
采用 `(q - zero) * scale`。

根据远程 H800 MIG 的 tile sweep，最终采用三档静态调度，避免按 328 个 Linear 形状做
大规模运行时 autotune：

| 阶段 | 条件 | `BLOCK_M` | `BLOCK_N` | `BLOCK_K` | warps | stages |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| decode | `M <= 4` | 16 | 128 | 64 | 4 | 3 |
| 小 prefill | `5 <= M <= 64` | 32 | 64 | 64 | 4 | 3 |
| prefill | `M > 64` | 128 | 64 | 32 | 8 | 3 |

作业 `177023` 的 sweep 中，大 prefill 调度从 `(64,64,32,4)` 改为
`(128,64,32,8)` 后：

- `M=128, N=15360, K=3840`：`7.330 ms -> 4.017 ms`；
- `M=512, N=15360, K=3840`：`27.945 ms -> 14.807 ms`。

## 框架接入

新增 `int4_triton` Linear 后端，并保留 `int4_reference` 作为 A/B 基线。模型 loader
根据后端选择创建量化层；`config.yaml` 已默认启用 `int4_triton`。在 CPU 输入上，
量化层仍回退到 reference 路径。

融合 kernel 与异步权重 offloading 没有新增 stream 或同步点。offloader 仍在一条传输
stream 上把下一层合并 payload 预取到双 GPU buffer，计算 stream 等待该层 ready event
后，kernel 直接读取 buffer 中的 qweight/scales/zeros 视图。kernel 不产生新的 H2D
请求，也不等待下一层权重。

## 正确性与精度

远程环境为 H800 PCIe MIG `1g.10gb`、4 vCPU、24 GiB 主机内存，Triton 3.7.1，
PyTorch 2.13.0+cu132。

作业 `176897` 的三组 CUDA 单元测试全部通过，覆盖：

- `M=1` decode；
- 多维输入展平；
- N/K 非整除 tile；
- `padded_in_features` 尾部；
- 对称和非对称 zero point；
- 可选 bias。

## Microbenchmark

作业 `177115` 使用真实 Gemma4 Linear 形状、BF16 activation 和 group size 64；
每项预热后用 CUDA Event 计时。临时显存为单次调用相对调用前 active allocation 的峰值，
包含输出。

| 形状/阶段 | reference | Triton fused | 加速比 | reference 临时显存 | fused 临时显存 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `M=1,N=15360,K=3840` decode gate | 6.633 ms | 2.211 ms | 3.000x | 355,860,480 B | 30,720 B |
| `M=1,N=3840,K=15360` decode down | 6.597 ms | 3.449 ms | 1.913x | 355,860,480 B | 7,680 B |
| `M=128,N=15360,K=3840` prefill gate | 6.621 ms | 4.024 ms | 1.646x | 355,860,480 B | 3,932,160 B |

reference 的约 339.4 MiB 峰值来自 unpack code、完整 BF16 权重及相关中间结果；融合路径
的记录值等于输出张量大小，说明完整反量化权重临时张量已经消除。

## 同口径端到端 A/B

作业 `177087`（融合）与 `177115`（参考）使用相同的
`performance_public.jsonl` 第一条请求、250 个 prompt token、最多 32 个输出 token、
相同长期 checkpoint、batch 1、相同 warmup，并关闭 profiler：

| 指标 | `int4_reference` | `int4_triton` | 变化 |
| --- | ---: | ---: | ---: |
| TTFT | 1.598 s | 1.851 s | +15.8% |
| Mean TPOT | 1.540 s | 0.948 s | -38.4% |
| 总延迟 | 50.331 s | 31.866 s | -36.7% |
| 峰值 GPU allocated | 3,051,874,816 B | 2,703,799,296 B | -348,075,520 B |

prefill 的端到端 TTFT 仍有约 0.25 秒回退，说明不同投影形状与 offload 重叠的整体效果
不能仅由 gate microbenchmark 代表；decode 占该请求绝大多数迭代，因此 TPOT 的下降最终
带来明显总收益。

## CUDA Profile

最终 tile 的 profile 作业为 `177051`。profiler 会扰动 H2D，本次 profile 内测得总
延迟 37.389 秒，而无 profiler 作业为 31.866 秒；因此性能结论采用上一节无 profiler
的同口径 A/B，profile 只用于归因。

| 算子/事件 | Self CUDA | 占比 | 调用次数 |
| --- | ---: | ---: | ---: |
| `aten::copy_` | 18.349 s | 49.55% | 63,710 |
| `Memcpy HtoD (Pinned -> Device)` | 18.141 s | 48.99% | 1,536 |
| `_w4a16_gemm_kernel` | 17.972 s | 48.53% | 10,496 |
| `aten::mm` | 0.280 s | 0.76% | 32 |
| unrolled elementwise kernel | 0.101 s | 0.27% | 32,352 |
| `aten::mul` | 0.091 s | 0.25% | 33,920 |

上一轮 `int4_reference` profile 中，反量化相关 unrolled elementwise 为 9.746 秒、
另一类 128-thread elementwise 为 9.342 秒、`aten::mul` 为 9.092 秒、
`aten::sub` 为 5.979 秒、`aten::mm` 为 3.583 秒。融合后这些热点不再主导，权重
计算集中到单个项目自写 kernel；剩余 `aten::mul` 等主要来自模型其他逐元素计算。

同一最终代码的两次 profile 中，H2D 分别为 13.987 秒和 18.141 秒，说明远程共享环境的
PCIe/调度存在明显波动。kernel 自身在 prefill tile 调整后从 19.594 秒降到 17.972 秒。

## 完整 10 请求正式成绩

根据后续统一要求，本轮补跑完整 `datasets/performance_public.jsonl`，不截断各请求的
`max_new_tokens`。作业 `177213` 成功退出（exit code 0），结果文件包含完整 10 行。

长度分布为：

- 输入：250 x 2、500 x 2、1000 x 2、1500 x 2、2000 x 2，共 10,500 token；
- 输出：16 x 3、32 x 4、48 x 3，共 320 token。

| 指标 | 完整 10 请求结果 |
| --- | ---: |
| 请求数 | 10 |
| 生成 token | 320 |
| 正式 `elapsed_s` | 400.511 s |
| 请求吞吐 | 0.02497 requests/s |
| 生成吞吐 | 0.79898 tokens/s |
| 累计 prefill latency | 70.683 s |
| 加权 Mean TPOT（310 次 decode） | 1.0403 s |
| 最大 GPU allocated | 5,856,150,528 B（5.45 GiB） |
| 最大 GPU reserved | 10,005,512,192 B（9.32 GiB） |

运行 2000-token prompt 时 allocator 曾报告一次 1,048,576,000 B 分配失败（当时空闲
186,646,528 B），但任务随后继续并成功完成全部 10 条请求。该警告仍说明 eager attention
prefill 已逼近 10 GiB MIG 的容量上限。

正式成绩距离 36 秒目标还有 364.511 秒，当前耗时是目标的 11.13 倍。以 320 个输出 token
计算，目标至少需要 8.889 tokens/s，而当前只有 0.799 tokens/s。batch 1 下 10 条请求被
串行执行，320 次模型 forward 各自搬运 48 层权重，权重 H2D 和 decode W4A16 仍会被重复
支付；后续必须用更高有效 decode batch 摊薄权重搬运，并先用融合 attention/chunked
prefill 释放长序列显存，才能给批处理留出容量。

## 结论与下一步

本轮已经完成“反量化-GEMM 融合”目标：CUDA 路径不再物化完整高精度权重，单算子临时
显存显著下降，decode microbenchmark 加速 1.9--3.0 倍，同输入单请求总延迟下降 36.7%，
且 `delta_nll=0.08659336 < 0.1`。

这里的 31.866 秒是 **一条代表请求**，不是完整 10 请求入分布 workload 的总时间，不能
据此宣称最终 `elapsed_s <= 36` 已达成。profile 显示下一阶段最主要的两项仍是 H2D
权重搬运和 W4A16 kernel 本身；进一步可做 M=1 专用 GEMV 数据布局/归约、按真实各投影
形状细分 tile，并通过提高 decode batch 来摊薄每 token 的 1,536 次逐层 H2D。

补测后的本轮正式 10 请求成绩为 `elapsed_s=400.511`，未达到 36 秒目标；31.866 秒只作为同输入单请求 A/B 数据保留。
